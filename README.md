# 并发观测台（隔离级别沙箱 + LISTEN/NOTIFY 迟到观测）

给数据库工程师的两个小工具，共用同一个 PostgreSQL 沙箱库与同一个 Docker Compose 栈：

- **隔离级别沙箱**（首页 `/`）：同一组并发写入在 READ COMMITTED / SERIALIZABLE 下各跑一轮，看数据会变成什么样；
- **通知迟到观测**（`/notify`）：复现「写端已提交，收端仍迟到」——两条连接监听同一频道，
  一条空闲、一条保持事务开启，分阶段列出两端实收并对照预期。

---

## 第一部分：并发写入观测台（隔离级别沙箱）

给数据库工程师的一个小工具：在改隔离级别之前，先看看**同一组并发写入**在不同隔离级别下会留下什么数据。

两个会话（A、B）按可编辑的脚本交错执行 SQL。同一组脚本、同一份初始数据，分别在
**READ COMMITTED** 和 **SERIALIZABLE** 下各跑一轮，页面上并排展示：

- 每一步的执行时间线（完成 / 出错 / 被阻塞 / 解除阻塞）；
- 每个事务的结局（已提交 / 已回滚 / 40001 中止）；
- 两轮事务都结束后，核对查询查到的最终数据。

每步有两种推进方式：

| 模式 | 含义 |
| --- | --- |
| `complete`（默认） | 等这条语句执行完成再推进下一步 |
| `blocked` | 语句在后台执行，等数据库确认它**被另一会话阻塞**（`pg_blocking_pids()`）就推进下一步；语句仍在飞，持锁会话可以继续走完自己的 `COMMIT` |

每轮有超时（默认 5 秒）：超时立即结束本轮，取消卡住的语句并**回滚未提交的事务**。
重跑总是从“初始数据 SQL”重新开始，两轮之间、两次运行之间互不影响。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8080        —— 隔离级别沙箱
#     http://localhost:8080/notify —— 通知迟到观测
```

`web` 依赖 `db` 的健康检查，数据库就绪后页面即可用。端口默认 `127.0.0.1:8080`
（本工具不做任何鉴权，会原样执行你贴的 SQL，请勿暴露到公共网络）。

## 页面与脚本语法

页面上三段可编辑内容：

1. **初始数据 SQL**：每轮开始前在控制连接上执行（可多条语句），负责把库重置到相同起点；
2. **交错脚本**：见下；
3. **核对查询**：两轮事务都结束后，在新连接上执行并展示结果。

交错脚本由步骤组成，每个步骤一行头部 + 一段 SQL：

```sql
@A complete
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

@B blocked
UPDATE accounts SET balance = balance - 200 WHERE id = 1;

@A complete
COMMIT;
```

- 头部：`@A` 或 `@B`，模式可写 `complete` / `blocked`（也接受 `完成` / `阻塞`），省略时是 `complete`；
- 事务由引擎按本轮隔离级别自动 `BEGIN ISOLATION LEVEL ...`，**脚本里不要写 `BEGIN`**，
  用 `COMMIT` / `ROLLBACK` 结束事务；脚本结束仍未提交的事务会被引擎回滚并记在时间线里；
- 一个步骤里可以写多条语句（结果只展示最后一条的），但建议一步一条，时间线更清晰。

## 内置样例

页面顶部可一键载入：

1. **两人同时撤班（写偏斜）**：`alice`、`bob` 两人在岗，规则是“至少留一人在岗”。
   两人同时撤班：各自确认在岗人数 ≥ 2 才撤。READ COMMITTED 下两笔都成功，
   核对查询显示 `on_duty_count = 0`——**无人值守**；SERIALIZABLE 下后提交者收到
   `40001 could not serialize access`，事务中止，仍有一人在岗。
2. **行锁等待（blocked 模式）**：两个会话更新同一行。B 用 `blocked` 模式确认被 A
   阻塞即推进，让 A 先提交。READ COMMITTED 下 B 在 A 的结果上继续（余额 700）；
   SERIALIZABLE 下 B 解除阻塞时收到 40001（余额 900）。
3. **超时回滚（演示）**：B 用 `complete` 模式等 A 的行锁，而 A 的 `COMMIT` 排在 B 之后
   永远轮不到 → 本轮超时，引擎取消卡住的语句并回滚两个事务，余额保持 1000。
   超时后立刻重跑，仍从初始数据开始。

## 自测

栈起来之后，在容器里跑端到端自测（覆盖：写偏斜两种结局、锁等待的阻塞确认与解除、
超时回滚、超时后重跑、blocked 模式未阻塞分支、脚本解析器；以及通知观测的
同笔合并 / 跨事务分别计数 / 回滚静默 / 迟到补收 / 超时保留与释放 / 参数校验）：

```bash
docker compose up -d --build
docker compose exec web python tests/selftest.py          # 全部
docker compose exec web python tests/selftest.py notify   # 只跑通知观测
```

也可以对着任意可达的 PostgreSQL 跑：

```bash
pip install -r app/requirements.txt
PGHOST=... PGDATABASE=... PGUSER=... PGPASSWORD=... python tests/selftest.py
```

## 实现要点

- `app/engine.py`：执行引擎。每个会话一条连接（`autocommit=True`，事务边界完全由
  SQL 语句控制），语句在工作线程里执行；`blocked` 模式通过控制连接轮询
  `pg_blocking_pids()` 确认阻塞；超时用 `pg_cancel` 取消在飞语句；收尾先回滚
  “没有在飞语句”的事务（可能借此解除另一会话的阻塞），再等在飞语句结束。
- 事务结局以服务器命令标签为准：`COMMIT` 一个已失败的事务时 PostgreSQL 实际返回
  `ROLLBACK`，页面会如实显示为回滚；`40001` / `40P01` 记为“已中止”。
- `app/script_parser.py`：`@A complete` / `@B blocked` 头部解析，带行号报错。
- `app/main.py`：Flask 页面与 `/api/run`、`/api/notify/run`。所有请求共用一个沙箱库，
  同一时刻只允许一轮实验（或一次通知观测）在跑，其余请求收到 409。
- `tests/selftest.py`：上面的端到端自测。

## 限制与说明

- 只支持两个会话；`blocked` 确认是 50ms 轮询，时间线精度有限；
- 引擎**不会**自动重试 40001（重试策略属于应用层，可在脚本里自行表达）；
- 单步可含多条语句，但只展示最后一条的结果；
- 初始数据 SQL 在 `postgres` 超级用户下执行，能力不设限——这是本地沙箱，不是多租户服务；
- 数据不持久化：每轮重置，容器删除即清空。

## 第二部分：通知迟到观测（LISTEN/NOTIFY）

入口：首页右上角「通知迟到观测」或直接打开 <http://localhost:8080/notify>。

### 复现的现象

PostgreSQL 的 `NOTIFY` 在写端**提交后**才投递；但如果收端连接此时正处于一个
打开的事务中（`idle in transaction`），服务端会先把通知挂起，直到该事务
`COMMIT` / `ROLLBACK` 才一次性送达。结果就是：写端早已提交，空闲的监听端立刻
收到，而另一条监听连接要等自己的事务结束才收到——看起来像“通知迟到”。

一次观测开三条连接：

| 角色 | 行为 |
| --- | --- |
| 空闲端 `idle` | `LISTEN` 后保持空闲（不在事务里），写端提交后应立即收到 |
| 持事务端 `held` | `LISTEN` 后 `BEGIN` 并保持事务开启，期间收不到任何通知 |
| 写端 `writer` | 分两笔事务发送（每笔可重复、可选 COMMIT / ROLLBACK），随后单独提交一条收尾通知 |

### 分阶段流程与预期

页面从**发送前**开始，逐步列出两端实收并对照预期：

| 阶段 | 动作 | 空闲端预期 | 持事务端预期 |
| --- | --- | --- | --- |
| 0 发送前基线 | 两端已 LISTEN、held 已 BEGIN | 0 | 0 |
| 1 第一笔写端事务 | 发送 N 次后 COMMIT / ROLLBACK | 提交则按“去重后的内容数”；回滚则 0 | 0 |
| 2 第二笔写端事务 | 同上 | 同上（与第一笔相同的内容分别计数） | 0 |
| 3 收尾通知（单独提交） | 单独一笔事务发送并 COMMIT | 1（未发送则 0） | 0 |
| 4 结束持事务端 | 空闲端确认收尾通知后才 COMMIT / ROLLBACK | 0（无新增） | 之前所有已提交通知 |

计数规则（由引擎算出预期，逐阶段比对实收）：

- **同笔相同通知合并**：同一事务内相同内容重复发送多次，只投递 1 条；
- **跨事务的相同通知分别计数**：不同事务各发一次相同内容 → 2 条；
- **回滚不增加收件**：`ROLLBACK` 的事务不产生任何通知，两端都不增加；
- 持事务端的补收给它自己的事务如何结束无关——即使 held 自己 `ROLLBACK`，
  写端已提交的通知仍会补发。

### 可调参数

- 频道名（需符合标识符规则；默认 `notify_late_demo`）；
- 两笔写端事务各自的：通知内容（多行，每行一条，同笔内自动去重）、每行重复次数、结束方式（COMMIT / ROLLBACK）；
- 收尾通知：是否发送 + 内容；
- 持事务端的结束方式（COMMIT / ROLLBACK）；
- 整体超时（默认 8 秒）。

### 超时行为

任一阶段等待实收超过整体时限：该阶段标为**未确认**（保留此前及本阶段已收到的
内容，并注明“实收 X 条 / 预期 Y 条”），后续阶段标为**未执行**；收尾时回滚 held
仍未结束的事务、关闭全部连接，并在页面下方单独列出“释放连接后的迟到补收”
（这些内容不计入阶段对照）。

### 内置样例

1. **同笔合并 · 跨事务分别计数**：两笔都提交且发送相同内容 → 空闲端 2 条，
   held 事务结束后补收 3 条（两条相同 + 收尾）；
2. **回滚不增加收件**：第一笔发送 4 次后回滚、第二笔提交 2 个不同内容 →
   空闲端只收到第二笔的 2 条，held 补收这 2 条 + 收尾；
3. **持事务端以回滚结束**：写端两笔都提交，held 用 `ROLLBACK` 结束事务 →
   仍然补收全部已提交通知。

### 实现要点

- `app/notify_engine.py`：观测引擎。三条连接均为 `autocommit=True`，事务边界显式控制；
  `LISTEN` / `BEGIN` 完成后才开始阶段 0；用 `select()` + `conn.poll()` 收通知，
  记录每条到达时间；预期由 `build_plan()` 纯函数生成，`run_observation()` 逐阶段
  比对并在 `finally` 中释放全部连接。
- `app/notify_presets.py`：内置样例；`app/templates/notify.html`：页面；
  `main.py` 的 `/api/notify/run` 用独立的 `NOTIFY_LOCK`，同一时刻只允许一次观测。

### 通知观测的已知限制

- 依赖 PostgreSQL 在收端事务开启期间挂起通知的行为（9.0 起即如此，本例在 16 上验证）；
- 判定“迟到”的精度受 30ms 轮询 + 250ms 稳定窗口影响，展示的是阶段性子集，不是逐条精确时序；
- 频道名只支持普通标识符（字母 / 数字 / 下划线），不支持带引号的特殊字符；
- 同一时刻只允许一次观测；它与隔离级别实验互不加锁（观测不碰业务表），但两者共用沙箱库，
  不建议手动同时跑。
